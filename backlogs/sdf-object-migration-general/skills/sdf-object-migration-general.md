# NetSuite SDFオブジェクト移行 汎用ガイド(環境間移行)

NetSuite SDFプロジェクトで、ある環境(SB/QA等)から別の環境(本番等)へカスタムオブジェクト
(customrecord/customlist/field/role/center/script/workflow等)を移行する際の標準手順と、
実務で繰り返し発生する落とし穴をまとめたもの。**特定プロジェクトの環境固有情報(日本語パス対応、

このファイルを別プロジェクトへ導入する場合、以下は導入先で読み替えること:
- 「取得元環境」「デプロイ先環境」= 導入先プロジェクトの実際のauthid
- プロジェクトパスに日本語等ASCII外文字を含む場合、`object:import`/`file:import`が
  パス解決に失敗することがある(Windows上のSuiteCloud CLIで確認)。ASCIIパスの別プロジェクト
  (ミラープロジェクト)経由での書き込み運用が必要になるケースがあるが、これは環境依存の対応であり
  本ガイドの手順そのものではないため詳細は割愛する。導入先プロジェクトのパスに問題がなければ不要。

## 適用対象

「〇〇を移行して」「SBから取得してデプロイして」等、SDF経由でのオブジェクト移行を指示された場合。

## 前提

- 認証は `suitecloud account:manageauth --list` で対象authid(取得元・デプロイ先)が設定済みであることを事前に確認する。
- **Windows環境でのシェル選択に注意**: `object:import`等に`--destinationfolder`のような`/`始まりのパス引数を渡す場合は、**PowerShellから実行する(Git Bashは避ける)**。Git Bash(MSYS2ランタイム)は`/`始まりの引数をUnixの絶対パスと誤認し、Windowsパスへ自動変換してしまうため、`--destinationfolder`の値が壊れて「Objectsフォルダ配下に存在しない」という紛らわしいエラーになることがある。原因不明のエラーに遭遇したら、まずシェルを変えて再現するか確認する価値がある。`project:deploy`/`project:validate`/`object:list`等パス引数を取らないコマンドはシェルを問わず動作する。
- 読み取り専用コマンド(`object:list`)は環境切り替えのみで実行できる。書き込みを伴うコマンド(`object:import`/`file:import`/`project:deploy`)は、プロジェクトパスに問題がなければメインプロジェクトから直接実行できる。

## 手順

### ① 移行対象一覧をMDで作成・更新する

- ユーザー指定のscriptid一覧を移行対象管理ドキュメントとしてまとめる(既存なら更新、なければ新規作成)。
- 全体進捗の管理表(CSV等)がある場合は該当行ステータスも更新する。
- **移行元のscriptidは作業中に変わりうる**。UI操作で自動採番されたscriptid(例: `custform_<内部ID>_<アカウント番号>_<環境>_<連番>`)は、移行判断の過程でユーザーがUI上で意味のあるIDへ改名することがある。過去に作成した対象一覧をそのまま使うと`Record does not exist`になるため、**日をまたいだ対象一覧は着手時に必ず`object:list`で再突合してから取得する**。

### ② 取得元環境で実物を確認し、SDFでダウンロード(import)する

- `suitecloud object:list --type <type>` で取得元環境の実在scriptidを確認する。
- ユーザー指定一覧とアカウント実在レコードを突合する。ユーザー提供リストには誤記(アンダースコア位置の違い、桁の欠落、同一オブジェクトの重複記載、誤字等)が一定数含まれる。`Record does not exist`が出ても即断念せず、同名・同用途のオブジェクトが別scriptidで実在しないか確認する。**置換した場合は必ずユーザーに確認を仰ぐ(推測で確定させない)**。
- `suitecloud object:import --type <type> --scriptid <id1> <id2> ... --destinationfolder /Objects/<type>` でXMLを取得する。
  - 対象typeを初めて取得する場合、プロジェクト側に`/Objects/<type>`フォルダが存在しないと全件失敗する(`... does not exist.`)。事前にフォルダを作成しておく。
  - 一部タイプ(`workflow`/`customrecordtype`等)では、原因不明のツール不具合と思われるエラーで`object:import`が一律失敗することがある(Oracle公式の既知バグ報告もあるが、上記のGit Bash起因である可能性も高いので先にシェルを確認する)。それでも失敗する場合、対象タイプがSuiteQLテーブルとして公開されていれば`SELECT * FROM <table> WHERE internalid = N`のように内部IDで直接検索し、`object:import`を経由せず名称・scriptidを取得する回避策がある。
  - `object:import`は存在しないscriptidを混ぜてもバッチ全体を中断せず、IDごとに成功/失敗が返る。この性質を使うと「特定の形のscriptidがアカウントに存在しないこと」を総当たりで検証でき、`object:list`の取りこぼしが無いことの裏取りにも使える(読み取り専用のため副作用なし)。
- ユーザーが対象を「NetSuite画面のURL(内部ID)+名称」でしか指定できない場合は、§9(recid→scriptid特定)を参照。

### ③ 相違・懸念点があれば一旦停止する

以下のいずれかを検知したら、後続処理を進めずユーザーに提示して指示を待つ:

- ユーザー指定一覧に無いscriptidがアカウントに実在する(急いでいる終盤の作業ほど見落としやすいので、検知した時点で機械的に立ち止まる)
- 取得元に実在しない(`Record does not exist`)
- 取得したXMLの内容が想定と異なる
- バンドル/SuiteApp由来と疑われるオブジェクト
- 対象が標準レコードのデータ(location/subsidiary/department/classification/employee/currency等)である — これらはカスタムオブジェクトの「定義」ではなく標準レコードの「データ」であり、SDF(`object:import`/`project:deploy`)の対象外。移行はNetSuite UIの手作業かCSVインポートで行う(ただしカスタムレコードのデータ行は例外的にSDFで移行できる。§8参照)
- 初期値が「アカウント固有の値」形式のフィールド、またはフィールド仕様上受け付けられない初期値(時刻フィールドへの固定文字列等) — そのままでは新環境に持ち込めないため、初期値指定を外すか新環境の対応レコードを指定し直す
- 対象typeのSDFスキーマに列挙値の制約があり、移行したい値がその列挙に含まれない(例: 特定typeの`recordtype`が特定のトランザクション種別を受け付けない) — この種のエラーは機能(feature)不足エラーとメッセージの形が異なるため区別すること。列挙に無い値は`manifest.xml`のfeature指定等では回避できず、UI手動作成に切り替えるしかない

### ④ 問題なければSDF経由でデプロイ先へデプロイする

- 対象一覧にないオブジェクトは絶対に`deploy.xml`へ追加しない。プロジェクト内にファイルが存在していても対象一覧と突合してから追加する。
- `deploy.xml` の `<objects>` に対象パスを依存順(トポロジカル順)で追加する。新規オブジェクトファイルは必ず反映すること。ワイルドカード指定(`~/Objects/<type>/*`)も使え、フォルダ配下を丸ごと対象にしたい場合や、ワイルドカードでなければ関連ファイルが同梱されないタイプ(例: emailtemplateは`.xml`と本文`.template.html`が対になっており、個別列挙だと本文が欠落して検証が落ちる)で有効。
- **デプロイ順序は`deploy.xml`の記載順に依存し、`--dryrun`では検知されない**。依存先(customrecord/field/customlist/savedsearch等)は必ず参照元(centerlink/centertab/centercategory等)より前に記載する。順序を誤ると、保存検索等で「空のオブジェクトだけ作成される」不完全なデプロイが実デプロイでのみ顕在化することがある(この場合、空オブジェクトを一から作り直すより、デプロイ先UI上で不足分を手動追加する方が現実的なことが多い。ただし手動補完後は同じオブジェクトを二度と`deploy.xml`に載せない(再デプロイで空に戻る恐れがある))。
- **循環参照(A⇄B)は、真の循環依存が確認できない限りまず素直にデプロイを試す**。失敗した場合のみ、参照先を指すフィールド定義を一時的にコメントアウトしてデプロイ→成功後に復元して再デプロイ、という手順に切り替える。
- 自己参照フィールド(フィールドが自分自身を参照条件に持つ)は、SDFの構造的な制約で`project:deploy`が恒久的に失敗する。業務上必要な場合はフィールド自体はSDFで作成し、自己参照の設定のみNetSuite UIから手動追加する。
- 権限ブロックの`selectrecordtype`等、未移行の他オブジェクトへの参照が含まれる場合は、当該参照を削除してからデプロイする。第三者SuiteApp由来のリンクも同様(SDF管理対象外のため関連付けに失敗する)。
- 参照先オブジェクトは、既にアカウント上にデプロイ済みであっても**同一の`deploy.xml`バッチに含める**必要がある(`project:deploy`/`project:validate`はローカルのプロジェクトファイル単位で依存関係を解決するため)。依存を辿った結果さらに依存先が必要になる場合がある(連鎖)。`--dryrun`のエラーメッセージに列挙された`[scriptid=...]`を芋づる式に追加し、エラーが出なくなるまで繰り返す。
  - **代替手段**: 参照先XMLを`deploy.xml`に同梱する代わりに、`manifest.xml`の`<dependencies><objects>`へ参照先scriptidを`<object>`として列挙する方法もある。これで検証を通過でき、既にデプロイ済みの参照先を再デプロイせずに済む(意図しない上書きのリスク回避)。参照先が数百件に及ぶ場合は同梱方式より現実的。ドット付きサブフィールド参照も同じ表記のまま登録できる。参照先がデプロイ先アカウントに実在しない場合は検証フェーズで落ちるため、実在確認も兼ねられる。
- 依存関係を再帰的に辿って`deploy.xml`を組み立てる場合、role(customrole)を依存クロージャに含めると`customrecord ⇄ customrole`のような循環参照で検証が落ちることがある。ロールが既にデプロイ済みなら、ワークフロー等のバッチからroleタイプごと除外する。
- `suitecloud project:deploy` で実デプロイの前に必ず`--dryrun`でサーバー側検証を行う。ローカルの`project:validate`は権限相互参照など一部で誤検知することがあるが、`--dryrun`はサーバー側の実際の挙動に近い。ただし前述の通り、デプロイ順序起因の問題は`--dryrun`でも検知されないことがある。
- 一度に大量のオブジェクト(目安: 15件超、または数百件規模の作成/更新)をまとめてデプロイすると、サーバー側がタイムアウトすることがある。4〜5件程度の小さいバッチに分割して`project:deploy`を繰り返すことで回避できる。
- **UPDATE時、ペイロードに含まれない既存要素は削除されない(推定される仕様)**。フォームXMLから参照(ロール一覧の項目、非表示フィールドの参照等)を削除して再デプロイしても、デプロイ先の実データからは消えない。削除が必須な場合はNetSuite UI側で手動削除する。
- `deploy.xml`を編集する際は、対象が無効化(コメントアウト)されたセクションに紛れ込んで放置されていないか定期的に確認する。
- `deploy.xml`にファイルパスとして記載する際、scriptidは大文字小文字を区別しないがファイルパス自体は区別する。突合は大文字小文字を無視して行ってよいが、実際のファイル名と一致させること。
- Script/MapReduce等のXMLの一部フィールド(例: `status`)だけを変更してデプロイする場合でも、`<scriptfile>`が参照するJSファイル本体を`deploy.xml`の`<files>`に含めないと検証が失敗する(アカウント上に既にファイルが存在していても、ローカルのデプロイセットに含まれていなければ通らない)。
- 「`「recordtype」フィールドの<値>を使用するには…<FEATURE>機能を指定する必要があります`」のようなエラーは、該当featureが`<features>`に`required="false"`で既に載っていても発生することがある。`required="true"`に変えると通る場合があるが、これはデプロイ先アカウントで当該機能が有効であることを要求するため、取得元専用機能を安易に`true`にしない。

### ⑤ 依存先未解決でデプロイできなかったものをリストアップする

- 依存未解決でスキップ・失敗したオブジェクトを、依存先のscriptidと種類(type)とともに一覧化する。
- リストをユーザーに提示し、対応方針(先に依存先を移行する/参照を一時削除する/対象外とする 等)の指示を仰ぐ。

### ⑥ 確認事項・移行記録をMDファイルに残す

- 対象件数、取得状況、デプロイ状況、未解決の依存関係、対応内容を記録。
- 全体管理表(あれば)の各scriptidの`status`/`notes`列を更新。
- ユーザー確認・判断が必要な事項は都度まとめ、確定した判断内容を反映する。
- **内部ID直書き(§3参照)がある場合、デプロイ後の実機目視確認を必須項目として記録する**。検証(`--dryrun`/`--server`)通過は「参照が正しい」ことの根拠にはならない(§3-4参照)。

## 既知の落とし穴(事例集)

### 1. オブジェクト間の参照・依存関係

手順④の該当箇所を参照。要点: 自己参照は構造的にデプロイ不可/循環参照はまず素直にデプロイを試す/参照先は同一batchかmanifest.xmlのdependenciesで解決/デプロイ順序は`--dryrun`で検知されない/role循環参照に注意。

追加で覚えておくべき点:
- **クラシックセンター**はNetSuiteの組み込みセンター(scriptidを持たない)であり、それ自体はSDFオブジェクトとして取得できない。表示内容(タブ・カテゴリ・リンク)は`centercategory`/`centertab`/`centerlink`という別々のSDFオブジェクトとして実在し、これらを個別に移行する必要がある。
- `centerlink`(`custlink_*`)は`<url>`フィールドにURLを直書きする型のオブジェクトで、scriptid参照によるSDF解決の対象外。URLにクエリパラメータで内部ID(`cf=`、`id=`等)が含まれる場合、その内部IDは環境間で一致する保証がない(§3参照)。

### 2. `object:import` / `file:import` 特有の失敗パターン

- 「Objects must be placed under the Objects folder or any of its subfolders.」のようなエラーで一部タイプの`object:import`が一律失敗することがある。まずシェル(PowerShell/Git Bash)を疑い、次にOracle既知バグの可能性を疑う。回避策としてSuiteQLでの直接検索が使える場合がある(§②参照)。
- AMDパスエイリアス(カスタムの`@NAmdConfig`によるモジュール解決設定を使っている場合)は、アノテーションがエントリスクリプト自身に付与されていないと、デプロイ時静的検証が依存関係を解決できず失敗することがある。末端の依存ファイル側にのみアノテーションが付いていて、それをrequireするエントリスクリプト側に付いていないケースに注意。
- **保存検索(savedsearch)は列/フィルタ定義がエンコードされており、XML編集で直せない**。SDF XMLの`<definition>`要素にNetSuite固有の圧縮バイナリとしてエンコードされて格納されているため、存在しないフィールド・削除済みアイテムを参照した状態のまま`object:import`すると再現性を持ってエラーになる。SDF側・ローカルファイル側での回避策は無く、**取得元のNetSuite UIから保存検索自体を開き、問題の列・フィルタを削除(または修正)してから再度`object:import`で取得し直す**しかない。
- 上記と同じエラーメッセージが、`object:import`(取得)は成功するのに**実デプロイ時にだけ**発生することがある。この場合、scriptid・名前だけの**空の保存検索オブジェクトが作成されてしまう**(`object:list`では実在確認できるが、UIで開くと列が0件)。`deploy.xml`内で依存フィールドより保存検索を後ろに書くと症状が「作成失敗」→「読込み失敗(空オブジェクトは作成される)」に変化することがあるが、列・フィルタの中身までは解決しないことが多い。空オブジェクトを削除してやり直すより、デプロイ先UI上で不足分を手動追加する方が現実的な場合が多い(手動補完後は当該オブジェクトを`deploy.xml`に再記載しないこと)。
- scriptidは大文字小文字を区別しないが、`deploy.xml`のファイルパス指定は区別する。
- `savedcsvimport`等、SDFスキーマの列挙値が固定されているフィールド(`recordtype`等)は、NetSuiteのUI(インポートアシスタント等)が対応していてもSDFの列挙に無い値は機能設定でもXML記述でも回避できない。該当エラーは「機能不足」エラーとメッセージの形が異なるため区別すること:
  - 「〜を使用するには…機能を指定する必要があります」→ 機能不足 → `manifest.xml`のfeatureを`required="true"`にする
  - 「オブジェクト・フィールド<field>は<値>にしないでください」→ **スキーマの列挙値に無い(回避不可)** → UI手動作成に切り替える
  - 切り分けには、最小構成のプローブXML(対象フィールドだけ差し替え)を`--dryrun`のみで試すと、対象アカウントに何も作成せず拒否/通過を確認できる。

### 3. スクリプト・設定値・保存検索フィルタへの内部ID直書き(対照表が必要)

SDFはscriptid同士の参照は環境間で解決するが、**scriptidを介さない内部ID直書き**はSDFの対象外であり、
取得元/デプロイ先で値が一致する保証がない。対照表なしでの移行は避ける。該当パターン:

**(a) スクリプト本文(JS)の中**
- `record.load/transform`等の`id:`に渡す特定レコード行の内部ID
- `search.load({ id: N })`のように内部IDでsaved searchをロードしているケース(scriptid文字列でなく数値)
- subsidiary/location/employee/item/vendor/customer等マスタの特定インスタンスの内部ID直書き
- customlist値の内部ID参照(scriptidの`val_NNN_...`部分)
- N/searchのfilter/columnに直書きされた内部ID値
- `centerlink`の`<url>`に含まれるクエリパラメータ形式の内部ID

**(b) Script/Script Deploymentのパラメータ設定値**
- List/Record型のscript parameterが指す特定レコード(通知先employee、対象subsidiary等)。パラメータの「型定義」はSDFのXMLに含まれるが、**実際に設定されている値**は個別レコードの内部IDで環境間の一致保証がない。**必ず実機(UI)のParametersサブタブで目視確認する**こと。XMLの記載を鵜呑みにしない。

**(c) ワークフローの`<valueselect>`が標準レコードのデータ行を参照する場合**
- 標準レコード(location/subsidiary/department等)のデータ行は、`[ACCOUNT_SPECIFIC_VALUE]`というプレースホルダで出力され、そのままでは検証で拒否される(参照先が実在するかとは無関係)。**解決策: デプロイ先の内部IDを生の数値で直書きすれば検証・デプロイとも通る**。ただし内部IDは環境間で一致しないため対照表が必須。直書きはローカルXMLのみに残り、取得元から再取得すると`[ACCOUNT_SPECIFIC_VALUE]`へ戻るため、再取得のたびに対照表を見て再適用する。
- NetSuite組込みの標準ステータス値(受注ステータス・出荷ステータス等)は全アカウント共通のIDのため対照表不要。ユーザー作成のデータ行と区別すること。

**(d) 保存検索の`<definition>`内フィルタ値**
- 「カスタム・フォーム」条件のような、保存検索のフィルタが特定のカスタムオブジェクト(customform等)を指す場合、`<definition>`内には**生の内部IDのみ**が記録され、scriptidへは一切解決されない。内部IDはアカウントごとに独立採番されるため、別アカウントへデプロイした場合、同じ番号が別のオブジェクトを指す可能性がある(対照表なしでは検知不能)。
  - 展開・調査には、`<definition>`が`<ハッシュ>@GZC@<バージョン>@<base64>`形式でgzip圧縮・base64エンコードされていることを利用し、base64デコード→gzip展開すると可読なXML(`FilterValueDescriptor`の`<field>`/`<value>`ペア)が現れる。
  - 対応: SDF側・ローカルXML側での恒久対応は無いため、デプロイ後に保存検索を開き直し、フィルタ条件を目視確認・再選択する運用でカバーする。

対応優先順位: scriptid参照への置き換え(恒久対応) > 環境ごとに値を入れ直す運用の明確化(Script Parameter外部化) > 最終手段としての値の機械的置換。

### 4. `deploy.xml` 運用上の罠

手順④参照。追加:
- **`emailtemplate`は`deploy.xml`にフォルダのワイルドカードで指定しないと本文が欠落して検証が落ちる**。`object:import --type emailtemplate`はオブジェクト定義の`.xml`とメール本文の`.template.html`を対で出力するが、`deploy.xml`に`.xml`のパスだけを個別に列挙すると本文ファイルがデプロイセットに含まれず`Provide a non-empty template file.`で失敗する。`<path>~/Objects/emailtemplate/*</path>`とフォルダ丸ごとのワイルドカードで指定する。副作用としてフォルダ内の全テンプレートがデプロイ対象になるため、対象外のものは別フォルダへ退避してからバッチを組む。

### 5. デプロイ後・データ内容に起因するエラー

- 初期値が「アカウント固有の値」形式のフィールドは新環境にそのまま持ち込めない。初期値指定を外すか、新環境の対応レコードを指定し直す。
- フィールド仕様上受け付けられない初期値(例: 時刻フィールドに固定文字列)。初期値を外してデプロイし、必要なら新環境側で改めて設定する。
- ワークフローのcondition builderパラメータが「is not specified」で拒否される場合、パラメータ名に**全角括弧などの特殊文字**が含まれていないか確認する。エラーメッセージ側は正規化された表記で出る一方、XML側の表記と食い違って検証エラーになることがある。対処は該当箇所のみ機械的に半角へ置換する等だが、`<formula>`のCDATA内に正規表現リテラルが含まれる場合、置換関数の実装(置換文字列に`$&`等の特殊シーケンスを含めない)に注意する。この種の後処理はローカルXMLのみに残るため、取得元から再取得すると元に戻る点も踏まえる。
- ワークフローアクショングループ内の一部アクション種別(sublist表示アクション等)の組み合わせで、サーバー側検証が詳細不明のまま失敗することがある。原因の切り分けが難しい「予期しないエラー」は、アクションブロックを機械的に間引いた変種XMLを作って二分探索すると効率的。

### 6. コマンド使い分けの原則

- 実デプロイ前に必ず`--dryrun`でサーバー側検証を行う。ローカルの`project:validate`は権限相互参照など一部で誤検知することがあるが、`--dryrun`はサーバー側の実際の挙動に近い。ただしデプロイ順序起因の問題は`--dryrun`でも検知されないことがある。
- Script/MapReduce等のXMLの一部フィールドだけを変更してデプロイする場合でも、`<scriptfile>`が参照するJSファイル本体を`deploy.xml`の`<files>`に含めないと`--dryrun`が失敗する(アカウント上に既にファイルが存在していても、ローカルのデプロイセットに含まれていなければ検証を通らない)。

### 7. 運用・進め方の教訓

- ユーザー提供の移行対象リストは、誤記・重複・「対象外だが依存関係で実は必要なオブジェクト」を一定割合で含む。**リストを鵜呑みにせず、必ず`object:list`で実在確認してから進める**。
- 判断が必要な事項(業務的に使っているか不明なカスタムリスト、追加移行が必要な参照先等)は、進捗管理表とは別に、業務確認用のサマリを作ると非エンジニアへの確認がスムーズ。
- 対象一覧にないオブジェクトを検知した場合の「一旦停止」ルールは、終盤の急ぎ作業でも例外を作らない。
- 移行元側のscriptidは作業中に変わりうる(UI上での改名)。日をまたいだ対象一覧は着手時に必ず`object:list`で再突合してから取得する。

### 8. カスタムレコードのデータ行(instance)の移行

標準レコードのデータはSDFで移行できない(§3(c)参照)が、**カスタムレコードのデータ行だけは例外的にSDFで移行できる**。

**8-1. `object:update --includeinstances` でデータ行ごとXMLに落とせる**

```bash
suitecloud object:update --scriptid <customrecordのscriptid> --includeinstances
```

`--includeinstances`は**カスタムレコード専用**のオプション(`object:import`には無い。`object:update`のみ)。実行すると型定義のXMLに`<instances>`ブロックが追加され、`project:deploy`でそのままデータ行を作成できる。テキスト・数値・チェックボックス・`isinactive`はそのまま値が入るが、**参照フィールド(select/multiselect)は全て`[ACCOUNT_SPECIFIC_VALUE]`にマスクされる**(複数選択の区切りは`|`)。`<instance scriptid="val_...">`が同一性のキーになるため、再デプロイは同じ行のUPDATEになる(重複行は増えない)。

**8-2. 参照フィールドは生の内部IDしか受け付けない — scriptid記法は不可**

マスクを埋める際、参照先がカスタムオブジェクト(emailtemplate等)であっても`[scriptid=xxx]`のような記法は実デプロイで失敗する。**参照先が標準レコードでもカスタムオブジェクトでも、等しく内部ID対照表が要る**。customlistの選択肢を指す`[scriptid=customlist_xxx.val_...]`形式が通るのはフィールド定義側の話であり、instanceのフィールド値には適用されない。

**8-3. `project:validate --server`も`--dryrun`もinstanceの参照値を検証しない(最大の罠)**

不正な参照値・存在しない内部IDを入れても検証は「成功」と表示され、実デプロイで初めて弾かれるか、あるいは弾かれずに誤った参照のまま作成されてしまう。**検証が通ったことを「参照が正しい」根拠にしてはいけない**。対照ミス(実在するが別のレコードを指す)は機械では検出できないため、**デプロイ後の実機目視確認を手順に必ず含める**。

**8-4. 型定義は「デプロイ先から取得したもの」をベースにする**

取得元から取得した型定義には、権限設定(`<permissions>`)等のブロックが欠落していることがある。そのまま流すとデプロイ先の既存設定を消しかねない。**デプロイ先から`object:update --includeinstances`で型定義を取得し、そこに自前で組んだ`<instances>`だけを足す**のが安全。型定義とデータ行を1ファイルで扱う仕様上、「データ行だけデプロイする」ことはできず、型定義は必ず同時に上書きされる。

**8-5. マスクされた実値の取得はREST record APIを使う(SuiteQL不可)**

移行元のマスク前の値を取るには、REST record API(`GET /record/v1/<customrecord>/{id}?expandSubResources=true`)を使う。SuiteQLでは複数選択フィールドが`RELATIONSHIP FIELD`という文字列しか返さず使えない。`BUILTIN.DF`は複数選択の表示名がカンマ連結で返るため、値自体にカンマを含む場合(氏名等)は分離不能。RESTは複数選択が`{count, items:[{id, refName}]}`のコレクションで返り、内部IDと表示名の両方が取れる。

### 9. ユーザー指定が「レコード名 + 内部ID(URL)」だけの場合の scriptid 特定

保存したCSVインポートのように、業務側が**NetSuiteのURL(`...?recid=NNN`)と画面上の名称でしか対象を指定できない**オブジェクトがある。SDFはscriptidでしか対象を指定できず、`object:list`はscriptidしか返さないため、`recid` → scriptidの変換が必要になる。

**9-1. UI自動採番のscriptidには内部IDが埋まっている(強い手がかり)**

UI操作で作られたオブジェクトのscriptidは`custimport_<N>_<アカウント番号>_<環境>_<M>`のような形を取り、**`<N>`はそのレコードの内部ID(＝URLの`recid`)であることが多い**(NetSuiteの一般的な自動命名規則)。

**9-2. ただし「コピーで作られたオブジェクト」は`<N>`がずれる — 必ず名称で裏取りする**

UI上でオブジェクトを「コピー」すると、scriptidのベース文字列が引き継がれ末尾に文字・数字を足した別レコードが生まれる。この場合`<N>`はコピー元の内部IDのままで、自分の内部IDとは一致しない。したがって`<N>`一致は決定打ではなく、必ず`object:import`して`<importname>`等の表示名で裏取りすること。

**9-3. `<N>`で当たらないものは「全件importして名称マップを作る」のが早い**

recidで当たらなかったものは、取得元の全件を`object:import`で取得して名称の全数マップを作成し、名称から候補を絞り込む。名称マップは「対象外オブジェクトの要否判断」にも副産物として使えるため、対象外が多いタイプでは早い段階で作っておくとよい。

**9-4. それでも一意にならない場合は必ずユーザーに確認する**

同名のテスト用オブジェクト等が併存し、`<N>`でも絞れないケースがある。このときは推測でデプロイせず、業務側にNetSuite画面の「ID」欄を確認してもらう(手順③の「一旦停止」に該当)。

**9-5. 依存関係の全数突合の手順(参照先がデプロイ先にあるか)**

対象XMLの`[scriptid=...]`参照は、トップレベル参照とサブフィールド参照(`親.子`のドット表記)に分かれる。トップレベルは`object:list`の結果と突合できるが、サブフィールドは`object:list`には出てこない。デプロイ先から親customrecordを`object:import`し、XML内の`scriptid="custrecord_*"`を抜き出して突合する必要がある。`--dryrun`でも同じ結論は出るが、事前に突合しておくとユーザーへの確認事項を1回でまとめられる。

**9-6. SuiteQLで引けないタイプがある**

対象タイプによっては、SuiteQL経由での`recid`→scriptid変換ができない(無効な検索タイプとして拒否される)ことがある。その場合`object:import`して名称を読む以外に照合手段が無い。

**9-7. `object:import`は存在しないscriptidを混ぜてもバッチを中断しない → 総当たり検証に使える**

§2でも触れた通り、存在しないIDを混ぜても該当IDだけ「Record does not exist」として返り、バッチ全体は失敗しない。この性質を使うと「特定の形のscriptidがアカウントに存在しないこと」を総当たりで証明できる。読み取り専用で副作用が無いため、判断に迷ったら実行してよい。ただしサフィックスの桁数を仮定するため、想定外の桁数(手動コピー由来等)は拾えない点に注意。

### 10. スキーマ上の既知制約

**10-1. カスタムレコードのフィールド定義には「無効(isinactive)」を表す要素がそもそも存在しない**

`customrecordcustomfield`(カスタムレコードの各フィールド定義)のSDF XMLには、フィールド単位の有効/無効を表す`isinactive`要素がスキーマ上そもそも存在しない(Oracle公式スキーマで確認可能)。レコードタイプ自体の`isinactive`(1レコードタイプにつき1個)とは別物であり、混同しないこと。

- 移行先にまだ存在しないフィールドを新規作成する場合、`isinactive`を指定しようがないため、取得元側が無効でも移行先には**有効な状態で新規作成**されると考えられる。
- 移行先に既に存在するフィールドを更新(再デプロイ)する場合、UPDATE時の非削除挙動(§4参照)と同じ理屈で、**移行先の既存の有効/無効状態がそのまま維持され、上書きされない**と考えられる。
- 対応: フィールド単位の有効/無効差異はSDFで一切管理できない。差異が疑われる場合はNetSuite UI上で個別に目視確認し手動で揃えるしかない。

**10-2. File Cabinetフォルダの新規作成範囲(Account Customization Projectの制限)**

Account Customization Project(特定アカウントを対象とするSDFプロジェクト)では、SDFが物理的に扱えるファイル・フォルダの格納場所が公式ドキュメントで以下に限定されている:

- `FileCabinet/SuiteScripts/`
- `FileCabinet/Templates/E-mail Templates/`
- `FileCabinet/Templates/Marketing Templates/`
- `FileCabinet/Templates/Web Site Hosting Files/`
- `FileCabinet/Web Site Hosting Files/*/SSP Applications/<app id>/`

(SuiteApp Projectの場合は`FileCabinet/SuiteApps/<app id>/`のみが対象。)これ以外の場所にある業務用のトップレベルフォルダ(File CabinetルートにUI手動作成された各種フォルダ等。ソース上の`SuiteScripts`配下の同名フォルダとは別物なので混同注意)は、フォルダ属性ファイルを用意してもSDFでは新規作成もデプロイもできない。

- 対応: このようなトップレベルフォルダを新環境に再現する必要がある場合はSDFを諦め、NetSuite UIから手動作成するか、`N/file`モジュール(`file.Folder.create().save()`)を使った一回限りのスクリプトで作成する。フォルダ数が多い場合は、移行元でフォルダ構成をsearch/SuiteQLで抽出→JSON化→スクリプトで再現する方が手動UI作成より速い(再実行時の重複作成を避けるため、名前+親フォルダIDでの既存チェックを入れること)。
→ Oracle公式: [SuiteCloud Project Structure and File Components](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_4724963992.html) / [Modifying SuiteCloud Project File and Folder Attributes in an XML Definition](https://docs.oracle.com/en/cloud/saas/netsuite/ns-online-help/section_4847748457.html)
